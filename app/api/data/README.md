# Data codebook: AirX ColdChain QC test datasets

> **These datasets are synthetic.** They were generated by [`make_datasets.py`](make_datasets.py)
> (fixed seed 5300) to look like the logs a regional blood bank already keeps on paper. No real blood
> bank, patient or donor records are included.

```bash
python data/make_datasets.py      # regenerates all three scenarios, byte-for-byte identical
```

## The three scenarios

Every scenario folder has the same three files, the same 12 storage units and the same 2 backup
generators. Each one plants a single, known behaviour, so the tool's output can be checked against it.

| Folder | What we planted | What the tool should report |
|---|---|---|
| [`normal_operation/`](normal_operation/) | Nothing. Every unit's temperature is random noise around its set point; both generators start ~99% of the time. | All 14 items **Normal**, 0 active alerts, every Cpk > 1.33 (range 1.50–2.89). |
| [`temperature_degradation/`](temperature_degradation/) | **R-04**: compressor wear from day 17 (Oct 8), temperature rising +0.045 °C per reading (~0.27 °C/day), crossing 6 °C on Oct 14. **R-07**: thermostat knocked up 0.6 °C (~2σ) on day 24 (Oct 15); still inside spec. | **R-04 Critical** (excursion), flagged by the run rules **124 h (5.2 days)** before its first out-of-spec reading. **R-07 Warning** (rules 2, 3, 4) even though it never leaves the spec. |
| [`generator_failure/`](generator_failure/) | **G-02**: starter/battery problem in the last two months: 8 failed starts in the last 90 days, including the real blackout on 2026-10-06 and the latest test on 2026-10-19. Two run failures in its history (stopped 3 h into its most recent earlier outage; stopped 0.2 h into the August 2026 load test). | **G-02 Critical**, p chart signals in 2026 Q3 (4 of 16) and Q4 (4 of 5), P(start) 95.6%, R(8 h) 0.851, P(loss of cooling in an 8 h blackout) 18.7%, **$26,179** expected loss of the $140,200 of blood it protects. |

The first 14 days of every temperature log are clean in all scenarios. That window is the **baseline**
(phase I) the tool uses to set each unit's control limits.

## `units.csv`: the inventory list (one row per storage unit)

| Column | Type / units | Meaning | Where a blood bank gets it |
|---|---|---|---|
| `unit_id` | text, e.g. `R-04` | Label on the refrigerator, freezer or incubator | Equipment list / asset tag |
| `unit_type` | `RBC`, `PLASMA` or `PLATELETS` | What the unit stores. Sets the specification limits: RBC 1–6 °C, plasma ≤ −18 °C, platelets 20–24 °C | Known |
| `backup_generator` | text, e.g. `G-02` | Which generator powers this unit in a blackout | Facilities / electrical panel schedule |
| `units_stored` | count | Typical number of blood components in the unit | Inventory system or daily count |
| `value_per_unit` | USD | Replacement cost of one component | Finance / supplier invoice. **Our values ($215 RBC, $50 plasma, $550 platelets) are illustrative; set your own.** |

## `temperature_log.csv`: thermometer readings (one row per reading)

| Column | Type / units | Meaning | How it's collected |
|---|---|---|---|
| `timestamp` | `YYYY-MM-DD HH:MM`, local time | When the reading was taken | Technician writes it on the temperature chart |
| `unit_id` | text | Which unit (must appear in `units.csv`) | Label on the unit |
| `temp_c` | °C, 0.1 °C resolution | Reading of the unit's calibrated thermometer | Read every **4 hours** (6 per day), the usual manual interval when a unit has no continuous recorder |

30 days × 6 readings × 12 units = 2,160 rows per scenario.

**To collect this for real:** keep the paper temperature chart already on each unit, then type it into
a spreadsheet once per shift, or photograph it. No sensors, network or software install needed. That's
the Devpost "data collection challenge": the agency has no telemetry, so the proxy variable is the
reading staff already take.

## `generator_log.csv`: every time a generator was asked to start (one row per demand)

| Column | Type / units | Meaning | How it's collected |
|---|---|---|---|
| `test_date` | `YYYY-MM-DD` | Date of the test or outage | Generator logbook |
| `generator_id` | text | Which generator | Nameplate |
| `test_type` | `weekly_exercise`, `monthly_load`, `outage` | Weekly no-load exercise (15 min), monthly load test (30 min), or a real blackout | Logbook; real outages from the facilities incident log |
| `started` | 1 / 0 | 1 = started and took the load; 0 = failed to start | Logbook check box |
| `run_hours` | hours | How long it ran this time (0 if it didn't start) | Engine hour meter, before/after |
| `run_failure` | 1 / 0 | 1 = it stopped or failed while running | Logbook / incident report |

204 rows per generator over 3 years (Oct 2023 – Oct 2026): 157 weekly exercises, 36 monthly load
tests, and 11 real outages of 1–12 hours. The outages are the **same blackouts for both generators**
(they're at the same site), including the 2026-10-06 blackout.

**To collect this for real:** healthcare facilities already test emergency generators on a weekly and
monthly schedule (the NFPA 110 pattern) and sign a logbook. The only addition is writing the hour-meter
reading before and after each run.

## What the tool computes from these columns

| From | Statistic | Course concept |
|---|---|---|
| `temp_c` per unit | I-MR control limits from the first 14 days; 8 run rules; Cp, Cpk, Pp, Ppk vs the spec | Statistical process control; capability indices |
| `started` per quarter | p chart of failed starts (exact binomial limits when failures are rare); exact start probability | Attribute SPC |
| `run_hours`, `run_failure` | λ̂ = failures / run-hours, R(t) = e^(−λt), MTTF, 95% bounds | Exponential reliability |
| both, plus `units.csv` | P(loss of cooling) = 1 − p_start × R(t); dollars at risk | Series/parallel system reliability |

Full method notes: [`docs/SIX_SIGMA_METHODS.md`](../docs/SIX_SIGMA_METHODS.md).
